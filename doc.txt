Implement Phase 1 only. Do not implement later phases yet.

You are a senior software architect, Python backend engineer, DevOps engineer,
program analysis researcher, and AI/ML engineer.

I am building a research-oriented system called:

"Root Cause Driven CI/CD Pipeline Automation"

The goal is NOT to build another generic AI chatbot that reads CI/CD logs and
generates explanations.

The goal is to build an evidence-driven CI/CD failure diagnosis and verified
remediation system based on this workflow:

    FIND → ATTRIBUTE → EXPLAIN → FIX → VERIFY

The system must identify whether a CI/CD failure is a genuine regression,
flaky test, infrastructure/configuration problem, or unknown failure.

For genuine code regressions, it must determine the most likely responsible
code change using CI logs, stack traces, Git history, AST analysis, dependency
relationships, temporal information, and historical evidence.

It must produce an explicit human-readable evidence chain explaining why a
particular commit/change was ranked as the likely root cause.

Only after root-cause attribution should an LLM be allowed to generate a
constrained patch.

The generated patch must be verified inside an isolated Docker sandbox before
being recommended to the developer.

The system must NEVER automatically modify production code or deploy directly
to production.

The normal workflow must remain:

Developer → Git Provider → CI/CD → Failure → Your System → Diagnosis →
Verified Fix Proposal → Developer Review → Normal CI/CD → Deployment

============================================================
1. CORE RESEARCH OBJECTIVE
============================================================

The central research question is:

"How can program analysis and evidence-based commit attribution improve the
reliability of LLM-assisted CI/CD failure remediation?"

The system should investigate whether combining:

- CI/CD logs
- Git history
- stack traces
- AST/code structure
- dependency graphs
- flaky-test detection
- temporal relationships
- historical failure information
- transparent confidence scoring
- constrained LLM patch generation
- sandbox verification

can provide more trustworthy CI/CD remediation than simply sending raw logs
to an LLM.

Do NOT design the system as an LLM-first architecture.

The LLM must be one component inside an evidence-driven pipeline.

============================================================
2. IMPORTANT DIFFERENTIATION
============================================================

Existing systems already perform some combination of:

- CI log analysis
- failure explanation
- LLM-based root cause analysis
- automatic patch generation
- CI reruns
- self-healing workflows

Therefore, this project must NOT claim novelty simply because it uses an LLM.

The main focus of this implementation is:

1. Failure classification
2. Flaky-test detection
3. Code-level dependency analysis
4. Responsible commit/change attribution
5. Transparent confidence scoring
6. Human-readable evidence chains
7. Constrained patch generation
8. Independent sandbox verification

The system should be able to say:

"This is probably a flaky test."

or:

"This is most likely an infrastructure/configuration problem."

or:

"Commit ABC123 is the most likely responsible change with 91% confidence."

and explain WHY.

If there is insufficient evidence, the system must say:

"Insufficient evidence for reliable attribution."

Do not force a root-cause prediction.

============================================================
12. MODULE 7 — ROOT CAUSE ATTRIBUTION
============================================================

This is the core research module.

For each candidate commit, calculate multiple signals.

Required signals:

1. Temporal proximity
2. File overlap
3. Stack trace overlap
4. Function overlap
5. Dependency graph relationship
6. Git diff relevance
7. Historical failure relationship

Do NOT make the final score opaque.

Start with a transparent weighted scoring model.

Example:

score =
    0.20 * temporal_proximity
  + 0.20 * file_overlap
  + 0.20 * stack_trace_overlap
  + 0.20 * function_overlap
  + 0.15 * dependency_relationship
  + 0.05 * historical_evidence

Make weights configurable.

Normalize all scores to [0,1].

Final confidence = weighted score * 100.

Return ranked candidates.

============================================================
13. MODULE 8 — EVIDENCE CHAIN
============================================================

For every candidate, generate explicit evidence.

Example:

Candidate:
ABC123

Confidence:
91%

Evidence:

1. Commit modified auth/service.py.
2. Failure stack trace references auth/service.py.
3. Commit modified validate_token().
4. validate_token() lies on the failing test execution path.
5. Test passed before ABC123.
6. Test failed after ABC123.
7. No similar failure existed in previous successful executions.

Each evidence item must contain:

- signal
- observed value
- score contribution
- human-readable explanation
- source

Do NOT allow the LLM to invent evidence.

Evidence must come from actual collected data.

34. EXPECTED END-TO-END DEMO
============================================================

The final system must demonstrate this exact scenario:

1. Developer pushes a change.
2. GitHub Actions runs.
3. A test fails.
4. GitHub sends failure information to the backend.
5. Backend retrieves logs and metadata.
6. System extracts the failure.
7. System checks whether the test is flaky.
8. System determines it is likely a genuine regression.
9. Git history is analyzed.
10. Stack trace is analyzed.
11. Tree-sitter analyzes relevant source.
12. NetworkX dependency graph is constructed.
13. Candidate commits are ranked.
14. Confidence score is calculated.
15. Evidence chain is generated.
16. UI displays the diagnosis.
17. LLM receives only the relevant evidence and code.
18. LLM generates a minimal patch.
19. Patch scope is validated.
20. Patch is applied in a Docker sandbox.
21. Failing test is executed.
22. Related tests are executed.
23. Build is executed.
24. If all required checks pass, patch is marked VERIFIED.
25. System creates a proposed fix PR.
26. Developer reviews it.
27. No automatic production deployment occurs.

============================================================
35. IMPORTANT FINAL REQUIREMENT
============================================================

Before writing large amounts of code:

1. Inspect the current repository.
2. Determine what already exists.
3. Create a concise implementation plan.
4. Create the architecture documentation.
5. Create the project skeleton.
6. Implement Phase 1.
7. Run tests.
8. Only then continue to Phase 2.

Do not silently skip phases.

At every phase, tell me:

- what you implemented
- which files changed
- why they changed
- how to run it
- how to test it
- what remains

Do not claim a feature is complete until it has actually been implemented and
tested.

Do not fabricate GitHub API responses, CI failures, LLM outputs, confidence
scores, or verification results.

The final system should be a real working research prototype, not a UI mockup
or a collection of disconnected scripts.

The architecture should be extensible to GitLab CI, Jenkins, AWS, Vercel,
Render, etc., but implement GitHub Actions first.

Most importantly:

THE SYSTEM MUST BE EVIDENCE-FIRST, NOT LLM-FIRST.

The LLM is responsible for patch generation and natural-language assistance.

The deterministic/program-analysis components are responsible for collecting
evidence, building relationships, ranking candidates, enforcing scope, and
verifying the generated fix.
